# frontend

How pages load data, where state lives, how streams reach the screen, and
the patterns and anti-patterns that keep the interface honest. The visual
contract itself is `DESIGN.md`; this file does not repeat tokens or
component specs — it says how to build with them.

## 1. Design contract

### 1.1 DESIGN.md is law

If a color, size, radius, motion, or component isn't in `DESIGN.md`, it
does not exist yet: add it there first, then use it. SPEC 18 makes this
mechanical for color: Tailwind's palette is wiped in `src/app/globals.css`
(`--color-*: initial`) and only the token classes exist (`bg-surface`,
`text-dim`, `border-border`, `text-accent`, `text-warn`, `text-danger`,
`text-ok`, `bg-accent-wash`, …). `bg-zinc-800` produces nothing.

### 1.2 Type is a utility, not a class soup

`type-display`, `type-h1`, `type-h2`, `type-body`, `type-label`,
`type-spec`, `type-meta` (`@utility` blocks in `globals.css`) carry
size/leading/weight/tracking/case. Use them; never restate `text-[13px]`
next to one.

### 1.3 Numbers are mono and tabular

Every year, price, count, VIN, code: `font-mono` with tabular figures.
Year ranges come from `yearRange()` in `src/ui/format.ts` (`2001–2006`,
en dash, no spaces). No em dashes in interface strings; `·` joins clauses.

## 2. Data loading

### 2.1 Server components own data

Pages are async server components. `/search` reads `q` and `v` from
`await props.searchParams` (a Promise in this Next.js), calls `runSearch`
inside `<Results>` behind a `Suspense` boundary keyed on the query, and
renders `<Enrichment>` behind its own `Suspense` so a slow NHTSA never
blocks the vehicle list. No client fetch for search.

### 2.2 Page props come from generated types

`PageProps<'/search'>`, `LayoutProps<'/'>`, `RouteContext<'/api/runs/[id]/stream'>`
are generated by `next typegen` (part of `pnpm typecheck`). Use them; do
not hand-write param types.

### 2.3 Runs are the one client-tailed stream

The run page (`src/app/inspect/[id]`, `src/app/salvage/[id]`) renders
`<RunView>` (client). It `GET /api/runs/:id` for the record, then
`GET /api/runs/:id/stream?from=<lastSeq+1>` and reads NDJSON lines
(`{seq, at, event}`), reconnecting from the last sequence it saw. Everything
on screen is `reduceRun(events)` from `src/ui/run/lines.ts` — a pure,
tested projection. SPEC 30.

### 2.4 Starting work is a POST that returns 202

`POST /api/inspect` / `POST /api/salvage` validate with zod, start a
detached run, and answer `{ id, persisted }` immediately. The client
navigates to the run page and attaches. No long-lived request carries the
work.

### 2.5 Capability probes, not feature flags

`GET /api/inspect` reports which stages this deployment can run (key
present, persistence available, seed count). The UI reads it to state
limits up front instead of failing later.

## 3. State

### 3.1 URL first

Search state is the URL: `/search?q=…&v=<branch>.<vehicle>`; malformed or
out-of-range selections are ignored (`parseSelection`, `selectionParam`).
Dismissing an assumption chip is a link to the query without that token
(`queryWithout`). Every state is shareable and back-button safe. SPEC 19.

### 3.2 Runs are addressed by id

`/inspect/<runId>` and `/salvage/<runId>` are permanent; the record and
events come from the store. Refresh, share, revisit — same page.

### 3.3 Client state is ephemeral only

`useState` holds the stream buffer, reveal cadence, lightbox index, trace
toggle. Nothing a reload could not rebuild lives in client state.

## 4. Streaming choreography

- Console lines queue client-side and reveal one at a time (90 ms
  tightening to 40 ms as the queue deepens; instant once done). The cursor
  line is the one blinking element. Stage dividers render on stage change.
- `begin` events drive the stage rail; `stage` statuses close rows; `span`
  events fill the trace waterfall. Degraded stages render exactly one
  `meta` line in `--warn`.
- On `report`, the console collapses to its summary bar and the report
  staggers in (verdict banner first, sections at 60 ms; under 600 ms
  total). Nothing moves after that.
- `prefers-reduced-motion` removes all motion; the cursor holds solid.

### 5.1 The assessments workspace

The workspace is the one surface built from client components rather than
server-rendered data, because a saved assessment changes while nobody is
navigating and creating one has to survive an ambiguous failure.
`/assessments` awaits its generated `PageProps` and renders
`AssessmentWorkspace` with the one thing a query can carry — the VIN a
showroom action offered, read through `prefilledVin`; `/assessments/[id]`
awaits its own and hands `AssessmentView` the id. Both pages are that and
nothing else — no data loading, no layout. Every read and write goes through `assessmentRequest`
in `src/ui/assessments/client.ts` to
`/api/assessments/*`, which owns the session, the owner and the store. A create
that may or may not have landed keeps its idempotency key
(`retainCreationIntent`), so retrying resolves the same record instead of a
second one.

`AssessmentView` has no initial fetch of its own: the bounded poll of §8 makes
the first read and every one after it, with the record and the activity log on
separate loops and the record's loop owning the error banner. Sections receive
`SectionProps` (`data`, `busy`, `save`) and never fetch or recompute: money is
read from the saved decision, so a section cannot disagree with the assessment
about the number. A refused write resolves false and leaves what the reader
typed on screen.

### 5.2 A preset fills a form, and what it filled says so

A form whose defaults come from somewhere other than the reader owes them a
sentence. `BuyerFields` renders a preset selector above its fields and, under
it, one assumption chip per value the reader has not changed, in the grammar
`assumed: <label> = <value>` (DESIGN.md assumption chip, SPEC 2). Editing a
field drops that field's chip and moves the selector to `Custom`; choosing a
preset refills every field and restates the whole row. A jurisdiction the
reader typed is the exception on both counts: it is theirs, no preset states
one, so it survives a preset choice and never moves the selector — the
divergence test (`divergedFromPreset`) leaves it out for the same reason
`presetFor` and `nearestPreset` leave it out of their comparison, and a
selector that read `Custom` there would disagree with the preset
`buyerFromForm` would save. Its own chip still drops when it is typed.

The chip decision is per field, and it survives a save. A saved profile is
`custom` as soon as one value is the reader's own, so the chips are decided
against `nearestPreset(profile)` — the preset matching the most inputs, the
hobbyist wedge on a tie — and not against the profile's own name. A value equal
to that preset's, and untouched in this session, chips; everything else does
not. Deciding per form instead would silently drop eighteen assumptions the
moment someone typed their state.

The inputs stay uncontrolled. State is a seed profile, an edited-field name
set, and a counter whose only job is to be the `key` that remounts the seeded
inputs when a preset is chosen — so a preset fills the fields without the
component mirroring every keystroke. Edits are noticed by one `onChange` on
the `fieldset`, which reads the changed element's `name`; the selector's own
radios are the one name it ignores.

The pure half lives in `buyer-form.ts`, alongside the `FormData` reader that
the submit handler calls: the chip text, the option labels and the derived
preset name are testable without a DOM, in the payload-builder grammar of §5
and `payloads.ts`. The name a submitted profile carries is derived from its
values, never from what the selector last showed.

## 6. Anti-patterns

- Fetching in `useEffect` for anything a server component can render.
- Client state that mirrors the URL.
- Off-token colors, radii above 4px, gradients, shadows other than the
  popover, emoji, spinners, skeletons, toasts (all prohibited by DESIGN.md).
- Confidence percentages, "clean history", or any model opinion presented
  as fact.
- Hand-formatted year ranges or hyphens where the en dash belongs.
- Uppercase `meta` for match reasons (they are explanations, sentence case).
- Rendering a finding without its citation, or a stage failure without its
  meta line.
- Importing an SDK, `process.env`, or a default caller from `src/ui/`.
- A poller with no stop condition, or one that remounts a form someone is
  typing into (8).

## 7. Adding a page

1. `src/app/<route>/page.tsx` as an async server component using the
   generated `PageProps`.
2. State in the URL; data via a domain function; `Suspense` around anything
   that can be slow, keyed on its inputs.
3. Components in `src/ui/`; pure formatting in `format.ts` with tests.
4. Every stage the page depends on renders its `StageStatus` line.
5. Add the tab to `src/app/nav.tsx` only if it is a top-level surface.
6. If a new visual element is needed, DESIGN.md first.

## 8. Bounded polling

### 8.1 A page polls only when there is nothing to tail

A run has an event stream, so the run page tails it (2.3). A saved assessment
has none: it changes when the agent commits a revision to the store, from work
that may be running in another process entirely. A page in that position
re-reads the record on a schedule. Nothing else polls; anything a server
component can render, and anything with a stream, is covered by 2.1 and 2.3.

### 8.2 The schedule is pure, and it ends

`pollIntervalMs(status, msSinceRevisionChange)` in
`src/ui/assessments/polling.ts` is the entire schedule: 1500 ms while the
record is active or investigating, 5000 ms once a minute has passed with no
revision change, and `null`, meaning stop, for a stopped record that nothing
but a manual action can change. `useBoundedPoll` runs it. It reads the status
and the last revision change from refs the response itself wrote, not from a
render that may not have happened, so a record that has just stopped is not
polled again. It skips the request while the tab is hidden, and a restart key
brings a stopped loop back after an action that could have restarted the work.

### 8.3 A failed poll states itself and the next success clears it

The poll that owns the record owns the error banner. An action's own failure
is separate state, so a poll landing a second later cannot erase what a save
just said. A secondary poll degrades in its own section with one `meta` line,
like any other degraded stage, rather than fighting for the banner.

### 8.4 A poll never takes back what someone is typing

A form seeded from a polled record may only be re-seeded while nobody is
editing it. `useSeededForm(revision)` pins the seed to the revision an edit
started from and reports the record as stale when it moves underneath, so the
page says the saved values changed instead of discarding the input. Never key
a form on its own data.
