# deployment

How paddock reaches production: one Vercel project holding two services,
deployed from `main` by the Git integration, gated by app-level auth, with
detached runs kept alive by `after()`. Lightweight on purpose; every step
below is reversible.

## 1. Topology

One project, two services. `withEve()` in `next.config.ts` wraps the Next
config: the Next app stays the default app, and the agent in `agent/` becomes a
second Build Output service that `/eve/v1/**` routes to before filesystem
routing. Neither is separately linked or deployed — `pnpm build` is the whole
deploy, because `withEve()` writes the eve service into the Build Output during
the Next build. Locally, a production start needs both halves built:
`pnpm build:all` (`eve build && next build`), then `pnpm start`, which serves
the agent from its own output on port `4274`.

| Piece           | Value                                                                                                                                                            |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Host            | Your Vercel project, Next.js preset, Node 24.x (`engines.node` is `>=24`; eve requires it)                                                                       |
| Production URL  | `https://your-project.vercel.app` (replace with your deployment)                                                                                                 |
| Source of truth | Your GitHub repository and configured production branch                                                                                                          |
| Trigger         | Push to `main` → production build; other branches build only if named `preview/*` (`vercel.json` `ignoreCommand`, `scripts/vercel-ignore.sh`)                    |
| eve service     | Generated by `withEve()` from `agent/`; serves `/eve/v1/**` only, and `src/proxy.ts` excludes that prefix because eve runs its own auth walk                     |
| Dispatch cron   | `agent/schedules/dispatch.ts`, cron `0 6 * * *` by default (`PADDOCK_DISPATCH_CRON` overrides at build time), discovered as a Vercel Cron Job on the eve service |
| Vehicle DB      | Turso (`DATABASE_URL` = `libsql://…`, `TURSO_AUTH_TOKEN`)                                                                                                        |
| Runs DB         | Postgres via `POSTGRES_URL` when set; memory store otherwise (visible degradation, SPEC 31)                                                                      |
| Assessments DB  | libSQL via `ASSESSMENTS_DATABASE_URL`; a `file:` URL is refused on Vercel (`docs/database.md` §6.3)                                                              |
| Auth            | `src/proxy.ts` + `AUTH_SECRET` / `AUTH_USERS` (`docs/auth.md`)                                                                                                   |
| CLI             | `vercel` (logged in as the project owner); `.vercel/project.json` links the directory                                                                            |

## 2. What a deploy is

1. `git push origin main` (after the local gate; `docs/workflows/integrate-and-deploy.md`).
2. Vercel runs `scripts/vercel-ignore.sh`: docs-only commit → skipped;
   otherwise `pnpm install` + `next build`.
3. The new deployment goes live at the production URL. Env changes are
   _not_ a deploy: after `vercel env add …`, run `vercel redeploy <url>`
   (or push a commit).

### 2.1 If the Git integration ever disconnects

`vercel api /v9/projects/<id>` shows `link: null`. Reconnecting needs a
GitHub login connection on the Vercel account (Account Settings →
Authentication → Login Connections, as the GitHub user that owns the
repo) and the Vercel GitHub App installed on the repo; then
`vercel git connect --yes` from this directory. Emergency deploys while
disconnected: `vercel --prod --yes` from a clean, pushed `main` (the CLI
upload respects `.gitignore`).

## 3. Environment matrix

All server-side, none `NEXT_PUBLIC_` (SPEC 17). Set with
`vercel env add <NAME> production` (choose _Sensitive_); list with
`vercel env ls`.

| Variable                | Required in prod | Purpose                                              | Absent →                                            |
| ----------------------- | ---------------- | ---------------------------------------------------- | --------------------------------------------------- |
| `DATABASE_URL`          | yes              | Turso vehicle DB                                     | Resolve stage degraded                              |
| `TURSO_AUTH_TOKEN`      | yes              | Turso auth                                           | Resolve stage degraded                              |
| `AUTH_SECRET`           | yes              | Session HMAC key (≥ 32 chars)                        | 503 fail closed (SPEC 40)                           |
| `AUTH_USERS`            | yes              | `user:scrypt$…` list                                 | 503 fail closed                                     |
| `AUTH_SESSION_DAYS`     | no               | Session lifetime (default 30)                        | 30                                                  |
| `ANTHROPIC_API_KEY`     | for agents       | Interpret fallback, themes, vision, research, triage | Search deterministic-only; inspect/salvage POST 503 |
| `POSTGRES_URL`          | recommended      | Durable runs, cross-instance tails                   | Memory store; "not persisted" meta line             |
| `EBAY_CLIENT_ID/SECRET` | no               | Live listings                                        | Listings section says so                            |
| `PADDOCK_DEBUG`         | never in prod    | Enables `/api/debug-run`                             | Route 404s                                          |

`VERCEL_ENV` is set by Vercel and switches auth to fail-closed
(`docs/auth.md §2`).

### 3.1 The assessment workspace and its agent

Everything below is read by both services: they are one project and share one
environment. The app and the agent must agree on `ASSESSMENTS_DATABASE_URL` or
the queue one drains is not the queue the other fills.

| Variable                            | Required in prod           | Purpose                                                                                        | Absent →                                                    |
| ----------------------------------- | -------------------------- | ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `ASSESSMENTS_DATABASE_URL`          | for `/assessments`         | The assessments libSQL database, shared by both services                                       | 503 `unavailable`; a `file:` URL is refused the same way    |
| `ASSESSMENTS_AUTH_TOKEN`            | with a remote libSQL URL   | libSQL auth for that database                                                                  | The client cannot connect                                   |
| `PADDOCK_AGENT_TOKEN`               | for research               | Bridge credential the app sends and `bridgeAuth` verifies                                      | Runs answer `accepted: false, reason: agent_not_configured` |
| `PADDOCK_AGENT_URL`                 | no (optional)              | Names a standalone agent; the co-hosted one is same-origin                                     | The deployment's own origin (`VERCEL_URL`) is used          |
| `PADDOCK_AGENT_MODE`                | no (default `fixture`)     | `fixture` or `live-coordinator`                                                                | `fixture`: no provider calls, labeled results               |
| `PADDOCK_AGENT_LIVE_ACK`            | live coordinator only      | Must be `yes` to admit paid coordination                                                       | `modelMode()` refuses live mode                             |
| `PADDOCK_AGENT_MODEL`               | live coordinator only      | Gateway model id                                                                               | `modelMode()` refuses live mode                             |
| `AI_GATEWAY_API_KEY`                | live coordinator only      | AI Gateway credential                                                                          | `modelMode()` refuses live mode                             |
| `PADDOCK_AGENT_ALLOW_LIVE_EVIDENCE` | no                         | `yes` plus live mode enables real vPIC/eBay/photo adapters                                     | Recorded evidence only                                      |
| `PADDOCK_DISPATCH_CRON`             | no (build-time)            | Replaces the dispatch schedule's cron expression; read while `eve build` compiles the schedule | `0 6 * * *`, the Hobby-safe daily default                   |
| `VERCEL_AUTOMATION_BYPASS_SECRET`   | with deployment protection | Lets the app's server-to-server call past the challenge                                        | The bridge call reaches the protection page, not the agent  |

`AI_GATEWAY_API_KEY` is required by `modelMode()` for live-coordinator mode even
on Vercel, where eve's gateway could otherwise authenticate through project
OIDC: the setting is an explicit acknowledgement of paid coordination, not only
a credential.

## 4. Runs on serverless

- The POST that starts a run returns 202 immediately and calls
  `after(() => runCompletion(id))` so the function instance keeps running
  the detached generator; `export const maxDuration = 300` on
  `/api/inspect`, `/api/salvage`, `/api/runs/[id]/stream` bounds it (Hobby
  cap; Pro allows more). A run that outlives it is reconciled to `error`
  on the next list/read (SPEC 30).
- Serverless instances do not share memory: the record read
  (`GET /api/runs/:id`) and the tail can land on different instances than
  the POST. Persistence therefore matters on Vercel, and the manager is
  written for it: an instance that does not hold the run serves the record
  from the store, tails the store for the stream (1 s polls, blank-line
  heartbeats every 15 s, re-attach after 240 s), and only reconciles a
  `running` run to `error` once it is 15 minutes old
  (`reconcileInterrupted`, multi-instance mode when `VERCEL_ENV` is set). Without `POSTGRES_URL`
  the libSQL run store writes to the Turso vehicle DB (`docs/database.md
§3.2`), which is shared by every instance; only if that is also down do
  runs fall back to per-instance memory with the "not persisted" line. To
  move runs to Postgres instead: Vercel dashboard → Storage → Create → Neon
  (free tier) → connect to the project; set `POSTGRES_URL` (Production,
  Sensitive); run `POSTGRES_URL=<url> pnpm db:migrate` once; redeploy.
- The debug run route is behind `PADDOCK_DEBUG=1` and stays unset in
  production.

## 5. Build gating (`vercel.json`)

`ignoreCommand: bash scripts/vercel-ignore.sh` — exit 0 skips the build:

| Situation                                   | Result                      |
| ------------------------------------------- | --------------------------- |
| Production, code changed                    | build                       |
| Production, only `docs/**` / `*.md` changed | skip                        |
| Preview branch `preview/*`                  | build (same docs-only rule) |
| Any other branch                            | skip                        |

Local hooks + CI already proved the code; the build exists to ship, not
to test.

## 6. Verifying a deploy

```sh
vercel ls                                          # top row Ready
curl -sI https://your-project.vercel.app/ | grep -i "^location"     # /login?next=%2F
curl -s https://your-project.vercel.app/api/runs     # {"error":"authentication required"}
```

Then in a browser: sign in, `/search?q=e46 m3` resolves, `/inspect` →
pick a seeded listing → run page tails and finishes. `vercel logs <url>`
for anything odd. Failure paths: `docs/workflows/incident.md`.

## 7. Rollback and redeploy

- `vercel rollback` — promote the previous production deployment
  (instant; env as of that deployment).
- `vercel redeploy <deployment-url>` — rebuild the same commit (after env
  changes).
- `git revert` on `main` — the durable fix; a new deployment follows.

## 8. Costs and limits

- Function `maxDuration` capped at 300 s on Hobby; runs must finish inside it
  (the research workers' budgets are sized for this). Pro allows more.
- Model spend is gated by auth; the shared party's usage is yours. Rotate
  `AUTH_USERS` to end access (`docs/auth.md §6.2`).
- Vercel Workflow backs every agent turn: eve runs each session turn as a
  durable workflow and persists it there, which is what lets a turn resume
  across instances. Nothing configures it, but the team must have it; locally
  and self-hosted the same code writes `.eve/.workflow-data` instead. The
  **Agent Runs** tab under Observability needs enablement for the team.
- The project is on the **Hobby** plan, confirmed when the deploy of PR #6 was
  rejected with `cron_jobs_limits_reached`. Hobby accepts one cron fire per day,
  so a build declaring a more frequent expression fails at Vercel's `patchBuild`
  step rather than deploying.
- Vercel Cron invokes `agent/schedules/dispatch.ts`. The expression is
  evaluated in UTC and defaults to `0 6 * * *`, which turns every retry and
  watch refresh into a daily job; inline dispatch from the run route is
  unaffected. `PADDOCK_DISPATCH_CRON` replaces it at build time, and minute
  granularity is a Pro feature. Discovery is under Settings → Cron Jobs,
  execution history under Observability → Cron Jobs. One fire drains at most 20
  units of work.
- The coordinator is bounded per session, not per month: 12 provider attempts
  in live mode (`reserveLiveModelCall` counts them in the database, so a
  restart does not reset the count), 512 output tokens per call, a 30 s
  provider timeout, and eve's own session limits of 60,000 input tokens,
  6,144 output tokens and $0.25 (`agent/agent.ts`). Fixture mode, the
  production default, calls no provider at all.
- The agent has no `sandbox.ts` and `defaultTools: false`, so no Vercel Sandbox
  session is ever created and the build prewarms no sandbox template.
- Hobby has no queues and no paid deployment protection.

## 9. Local parity

`pnpm build && AUTH_SECRET=… AUTH_USERS=… DATABASE_URL=file:data/eval.db
pnpm start` reproduces production behavior including auth (cookie is
`Secure`, so use a browser on `http://localhost` — browsers exempt
localhost — or `curl -H "Cookie: …"`).
