# multi-agent

The build protocol for several agents (or humans and agents) working on
paddock at the same time. It optimizes for zero shared mutable state
between workers, one integration point, and no hand-merged artifacts.

## 1. Principles

- One branch per task, one worktree per branch, one agent per worktree.
- Only the primary checkout is ever on `main`, and `main` only moves by
  merging a PR; the primary checkout is where you `git pull` after a
  merge, never where you commit.
- Tasks own files. Two concurrent tasks never edit the same file; shared
  files are "merge-last" and edited append-only.
- Generated artifacts are regenerated by the integrator, never merged.
- The plan lives on disk (`docs/initiatives/`), not in anyone's context.

## 2. Setting up a worktree

```sh
pnpm wt new feat/<slug>        # from main; or: pnpm wt new feat/<slug> <base>
cd .worktrees/feat/<slug>
PORT=<printed> DATABASE_URL=file:data/eval.db pnpm dev
```

`scripts/worktree.sh` gives each worktree: `node_modules` from the shared
pnpm store (seconds, offline), a copy of `.env.local`, `data/eval.db`
built from the checksum-verified public EPA sample, a symlink to `data/ymm.db` when the
primary has one, and a stable port in 3100–3999 derived from the name.
`.worktrees/` is gitignored. Postgres (docker, `:5433`) is shared across
worktrees — runs from any worktree land in the same local DB, which is
fine.

Remove with `pnpm wt rm feat/<slug>` (refuses on uncommitted changes;
`--force` overrides). `pnpm wt ls` lists.

## 3. Claiming work

Work is planned in the initiative document's task table
(`docs/initiatives/<current>.md §4`): id, task, files, verify, status.
An agent claims a task by setting its status to `doing` and its branch
name in the log, on its own branch, in its first commit — the integrator
sees claims as branches land. When several agents start at once, the
coordinator assigns ids up front so claims cannot collide.

Rules for the table:

- The `files` column is the ownership boundary. If a task needs a file
  another `doing` task owns, it waits or the coordinator re-cuts the tasks.
- A task that discovers it needs more files adds them to its row before
  touching them.

## 4. Merge-last files

Files many tasks touch. Edit append-only (new rows, new sections, new
lines at the end of a list) so rebases apply cleanly:

| File                                             | Rule                                                                            |
| ------------------------------------------------ | ------------------------------------------------------------------------------- |
| `SPEC.md`                                        | Append rules; never renumber (`docs/workflows/spec-update.md`)                  |
| `docs/**/*.md`                                   | Append sections; never renumber                                                 |
| `CLAUDE.md`                                      | Append routing rows / bullets                                                   |
| `package.json` scripts, deps                     | Append; the integrator runs `pnpm install` after rebase                         |
| `.env.example`                                   | Append                                                                          |
| `evals/queries.jsonl`                            | Append lines                                                                    |
| `evals/results.{md,json}`, `evals/history.jsonl` | Never edit by hand; integrator regenerates (`pnpm eval`)                        |
| `data/public-generations.json`                   | Independent source review; never infer generation windows from catalog coverage |
| `AGENTS.md`                                      | Regenerated by `next dev`; commit whatever it produces                          |

## 5. Integration protocol

Performed by whoever holds the primary checkout on `main`
(`docs/workflows/integrate-and-deploy.md` is the step list):

1. `git fetch origin && git switch main && git pull --ff-only`.
2. In the worktree: `git rebase main`. Resolve conflicts (artifacts:
   take either side). `pnpm install` if `package.json` changed.
3. Gate: `pnpm typecheck && pnpm lint && pnpm docs:check && pnpm test &&
pnpm eval` — if `evals/results.*` changed, commit them on the branch.
4. `git push -u origin <branch>` (pre-push gate) and `gh pr create --fill`.
5. `gh pr checks --watch`, then `gh pr merge --squash --delete-branch`.
6. `pnpm wt rm <branch>`; flip the task to `done` in the initiative doc
   and append a log line (docs-only PR: CI skips the job, merges fast).

Only one branch integrates at a time; the next agent rebases onto the new
`main` before its own gate.

## 6. Coordination without a chat channel

- The initiative doc is the shared state; read it before starting and
  after every integration.
- Branch names carry the task id when one exists (`feat/c3-rate-limit`).
- A blocked task sets `blocked(<why>)` in the table so nobody waits on it
  silently.
- Manual human actions go in the initiative's §5 list, never as a question
  buried in a commit body.

## 7. Resource sharing

| Resource            | Shared?       | Note                                                            |
| ------------------- | ------------- | --------------------------------------------------------------- |
| pnpm store          | yes           | Installs are hard links; fast and disk-cheap                    |
| `data/ymm.db`       | yes (symlink) | Read-only from the app; rebuild only from the primary           |
| `data/eval.db`      | per worktree  | Built from the verified public EPA sample; cheap                |
| Postgres (docker)   | yes           | One container on `:5433`; migrations idempotent                 |
| Dev port            | per worktree  | Derived from the name; printed by `pnpm wt new`                 |
| `.env.local` (keys) | copied        | Same Anthropic key; watch spend when many agents run live paths |
| Vercel              | `main` only   | Branch pushes do not build unless `preview/*`                   |

## 8. Anti-patterns

- Two worktrees on the same branch (git prevents it; do not work around).
- Editing `evals/results.*` to resolve a conflict.
- A "big integration branch" that collects several tasks before hitting
  `main` — integrate each task as it finishes.
- Renumbering a SPEC rule or docs section to make room.
- Committing from the primary checkout while it holds uncommitted
  integration state for someone else.
